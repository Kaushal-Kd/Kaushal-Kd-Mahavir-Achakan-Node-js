## 9. Cross-cutting regression and rollout gates

- [ ] **Offline queue and replay:** In the desktop test profile, queue supported delivery, return, booking edits, replacement, reassignment, and condition operations offline; reconnect and verify one scoped transaction per operation, original quantities, honest pending/error state, and no duplicate money/WhatsApp effects. Earlier pending or failed commands block later commands in the same shop/user scope until resolved or explicitly removed. Commands are persisted before the first network attempt; switching accounts cannot reassign a retry. Genuinely online-only identity/OTP/customer-master setup should say so rather than pretending to save offline.
- [ ] **Atomic booking edits:** Edit the advance/security controls and trigger an invalid account or stale-product failure. No payment or header/line change may persist. Retry a successful edit with the same command key: no duplicate payment. Edit notes only after a partial security refund: do not recollect the difference. Stale expected receipt totals or configured security amount must require refresh.
- [ ] **Authorization and isolation:** Repeat sensitive writes as restricted user and another-shop user. Rejections leave no partial data. Super-admin user overrides and shop role defaults must not leak across shops.
- [ ] **Stale forms and concurrency:** Open the same booking in two test windows, change a lifecycle/money field in one, then submit stale data in the other. No silent overwrite of delivered/returned quantities, held balances, or current availability.
- [ ] **No surprise side effects:** Reading reports, downloading PDFs, changing filters, previewing a bill, and canceling dialogs must not post payments, mutate stock, send messages, or queue writes.
- [ ] **Fresh migration chain:** On isolated MySQL, run every migration in real sorted order. Do not skip a failing historical migration just to make tests pass.
- [ ] **Measurement preservation:** Verify both fresh and partial-stage custom-order measurement fixtures. New preflight `20260901115900_prepare_custom_order_measurement_rename.js` archives values and creates the staging column; unchanged historical rename runs; `20260901120100_restore_custom_order_measurements.js` restores mapped and unknown data. Keep the archive, including conflict/raw values. An already-recorded historical migration remains untouched; reruns do not overwrite later business edits.
- [ ] **Migration history safety:** The schema-history sync helper must not falsely mark explicit-run data repairs applied. Historical migration files are unchanged. Before rollout, obtain a restorable database backup and rehearse on a clone with existing populated history; a successful empty-database run is not enough.
- [ ] **Rollback planning:** Do not use blind `migrate:rollback`, seed, reset, or manual history edits on a business database. Data-repair down steps intentionally preserve archives; rollback needs a reviewed restore/forward-fix procedure. Keep migration time, backup identifier, and operator approval with the release record.
- [ ] **External gates:** Complete actual browser/mobile checks, SMTP OTP, WhatsApp test delivery/reconnect, attachment storage, report downloads, and physical printer samples before declaring those features verified.
- [ ] **Release discipline:** Review the final diff, rerun affected tests after fixes, then run the complete suite/build once more. Keep secrets/temp artifacts excluded. Do not push; local commits, if desired, require a separate reviewed staging selection.

## Feedback loop and final sign-off

For each failure: capture the smallest synthetic reproduction, inspect the relevant frontend/service/schema/transaction together, write a regression for the incorrect business behavior, implement the focused fix, rerun that test, ask an independent reviewer to challenge the assumptions, and rerun the broader suite. A test that asserts the old incorrect immediate-income behavior must be corrected to the agreed held-money semantics, not used to justify reverting the fix.

Stop production rollout for any unresolved money duplication/loss, cross-shop access, migration data loss, login lockout, incorrect stock quantity, or sent-to-wrong-recipient failure. A blocked external test stays BLOCKED; absence of a connection is not a pass.
